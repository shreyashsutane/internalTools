Real-Time Operational Email Alerts: Architecture, Formation & Delivery

The definitive end-to-end technical guide explaining how user interactions (login, entity analysis, database migrations, and rollbacks) are captured, verified against Google OAuth, converted into responsive dark-mode HTML, and delivered to shreyashs14102002@gmail.com via encrypted Gmail SMTP without storing passwords in browser code.

01 The 30-Second Beginner Overview (The Postal Analogy)

If you are new to web development, cloud functions, or SMTP mail servers, here is how the email alert system works conceptually:

1. You Trigger an Action

You click "Verify Token", "Analyze Entities", or "Copy Entities" in your browser. The browser drafts a message: "Operator X just copied 42 rows!" and sends it to our serverless Cloud Function.

2. The Security Checkpoint

Our serverless Cloud Function checks your Bearer Token directly with Google's OAuth2 servers to verify your real identity, saves an audit log to Cloud Firestore, and prepares the HTML template.

3. The Secure Delivery

The server fetches your 16-character App Password from Google Cloud Secret Manager, connects to Gmail over TLS 1.3 via Nodemailer, and delivers the email into your inbox.

Why couldn't the browser just send the email directly?
❌ Sending from Browser (Dangerous):

Any user could open Developer Tools (F12) to inspect memory and steal your Gmail password, or manipulate the JavaScript to forge fake audit alerts.

✅ Our Serverless Backend (100% Secure):

Your Gmail password is encrypted in Google Secret Manager. The backend asks Google directly for the verified operator email address.

03 The 4 Operational Event Triggers

The portal dispatches an email notification whenever any of the following 4 critical operations occur:

1. User Login AUTHENTICATION

Triggered when an operator verifies their Google OAuth Bearer Token.

Subject: [GCP Portal] User Login: operator@company.com
Details: Verified token successfully. Loaded 14 accessible projects.
2. Entity Analysis DATASTORE_ANALYZE

Triggered when an operator runs an entity scan to compare source and target tables.

Subject: [GCP Portal] Datastore Analysis: auditor@company.com
Details: Analyzed 4 kinds. Total: 180 (identical: 150, mapped: 20, diff: 10).
3. Datastore Copy / Commit DATASTORE_COPY

Triggered when entities are written to the destination project/database.

Subject: [GCP Portal] Datastore Copy: operator@example.com
Details: Batch 1/1 copied 42 entities across kinds: UserProfile, Orders.
4. Rollback Revert DATASTORE_REVERT

Triggered when an operator restores a previous batch from audit logs.

Subject: [GCP Portal] Datastore Revert: admin@example.com
Details: 1-Click Rollback executed for batch-9981. Restored 42 entities.

04 How the HTML Email is Formed & Rendered

Instead of sending heavy raw database snapshots or plain unformatted text, the backend dynamically builds a responsive, dark-mode HTML email using a 4-step assembly pipeline:

Step A: Extracting & Sanitizing Data escapeHtml()

All dynamic user values (project IDs, entity counts, error messages) pass through escapeHtml() to convert reserved characters like <, >, and & into HTML entities so malicious code can never run.

const safeDetails = escapeHtml(log.details);
Step B: Dynamic Theme Colors & Badges Status Badge

The server computes the badge text and accent color depending on the execution outcome:

  • • SUCCESS: Green badge (#10b981)
  • • FAILED: Red badge (#ef4444)
  • • RESTORED / PARTIAL: Amber badge (#f59e0b)
Step C: Universal Inline CSS Styling Cross-Client CSS

Email clients (like Gmail on mobile, Apple Mail, and Outlook) often strip external stylesheet files. Therefore, our HTML uses inline CSS rules and responsive table/div structures so the email renders cleanly on any device.

Step D: Why HTML Summary instead of Raw Snapshot? Efficiency & Speed

A raw database backup can be hundreds of kilobytes or megabytes. Instead of clogging your email inbox with huge JSON attachments, the email delivers a concise human summary, while the complete 1-Click Rollback snapshot is preserved safely in Cloud Firestore.

06 Frequently Asked Security Questions (Beginner FAQ)

1 How does the system know the operator's REAL email address?

When the user logs in, they supply a temporary Google Cloud Bearer token. When a request reaches our Cloud Function, the server does not trust any email string sent in the body. Instead, it contacts Google’s OAuth token server (https://openidconnect.googleapis.com/v1/userinfo) with the token. Google responds with the authoritative user profile email.

2 Where is my Gmail App Password stored?

Your password is never saved in the source code or git repository. It is saved in Google Cloud Secret Manager under ALERT_GMAIL_APP_PASSWORD. Only our Cloud Function's dedicated service account has permission to read it during runtime execution.

3 What happens if Gmail SMTP is slow or times out? Will my database copy fail?

No. The email dispatcher is wrapped in an asynchronous non-blocking error handler: sendMutationAlertEmail().catch(...). If Gmail is unreachable, the audit record and database operations still complete with 100% success.

4 How do we prevent hackers from injecting malicious scripts into emails?

All dynamic parameters (project names, kind names, error logs) pass through our escapeHtml() sanitizer function, which converts HTML reserved characters (< ➔ &lt;, > ➔ &gt;, " ➔ &quot;) to make email rendering completely safe.
